## `chat` (18 rule(s))

The interaction protocol and communication discipline between Claude and the researcher -- turn-taking, confirmation-before-acting, output-to-file, cost awareness. Distinct from llm_output, which governs epistemic trust in generated content regardless of channel.

A genuine researcher judgement call is written to a `.md` review file with options and a decision blank, pointed to in plain chat. - **open-threads-carried-as-escalations** — The open threads register is carried in the escalation table as type='thread' (alias OT-nn), not edited as a markdown file. Claude manages each thread's lifecycle; the researcher gives feedback in chat, which Claude records verbatim the same turn, and there is no approval step. Every response to an item -- touched, narrowed, forward, ruling, note, closed, reopened, withdrawn, superseded -- is an escalation_thread_item_response row, recorded through Escalation.ps1 -Action Update -Id OT-nn -Item ... -ResponseKind ... -Respond ..., and written in full to the thread's history. A thread completes when its last open item is settled; a thread is withdrawn or superseded (-SupersededBy OT-nn) with its open items settled in the same call. Notes and comments on a thread are Updates, never edits to the register file. The file _analytics/cross-cluster-web/open-threads-register.md is generated (Escalation.ps1 -Action Export -Type thread) and regenerated at session-close when a thread row changed in the session (SC12). Its quality, validity and integrity are audited at every start (Escalation.ps1 -Action ThreadAudit). Before every unit pull of a strand, the threads that bear on it are matched (Escalation.ps1 -Action Match -Cluster .. -Strong .. -Verse ..; -For nnnn records the match); held items and researcher questions are raised as threads at every ledger approval (Escalation.ps1 -Action Raise -Type thread).
