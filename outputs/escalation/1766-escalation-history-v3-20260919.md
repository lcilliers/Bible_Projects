> **short description (set this version):** App-wide bulk purge utility for soft-deleted rows
> **comment (set this version):** Researcher's own request this chat turn, raised while discussing #1765's supersede-vs-soft-delete question: 'we must create a utility that can bulk destroy soft deletes in the App as a whole, because there are huge data redundancies building up.' Distinct scope from #1765 (which is specifically about ib_observation/ib_node re-reads) -- this is app-wide, across every table in both iba.db and bible_research.db that carries a deleted/delete_flagged soft-delete column (dozens of tables across this session alone: cluster_subgroup, cluster_subgroup_strong, strong, cluster_strong, word_registry, and many more).
> **context (set this version):** Not built this session (usage-limit context). Real design questions before this can be built safely, not mechanical: (1) per-table safety -- some soft-deleted rows may be referenced by FK from OTHER live rows (e.g. a superseded ib_observation once #1765's chain is built) -- a blind DELETE FROM table WHERE deleted=1 risks orphaning or FK-violating referencing rows; needs either a dependency-aware purge order or a per-table allow/deny policy. (2) retention window -- purge everything soft-deleted regardless of age, or only rows soft-deleted before some cutoff (giving a recovery window before physical deletion)? (3) which tables are even in scope -- likely driven by a query against cfg_column for columns literally serving as a soft-delete flag, cross-checked against cfg_table for any table explicitly marked as audit/history (which may need to be excluded from purging on principle, unlike ordinary operational tables). (4) dry-run/reporting -- almost certainly needs a preview-then-live discipline (same pattern as every other live-writing script in this app) showing exactly what would be purged, per table, before committing. Proposed shape: a new PS script (e.g. Purge-SoftDeletes.ps1) + cfg-driven per-table policy (governance.module.config), not a single blind script -- but the exact policy shape is the researcher's own call, not mine to invent unilaterally.
