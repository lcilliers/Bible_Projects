## 1. The flow in practice (accepted, v38)

**A. Before analysis: at the clustering stage (E3a).**
1. `iba/app/ps/Cluster-Assign.ps1` runs as it does today: codes into clusters (`cluster_strong`).
2. A new step, `cluster.surface_map`, runs per M cluster (T-2). For M18 it:
   - lists the 454 (code, surface) pairs with their hits;
   - sets the cluster's surface groups as `cluster_subgroup` rows, each with a kind: `group`,
     `qualifier` (E4), `not_this_sense` and `anomaly` (C4);
   - allocates each pair to one group with its reason (C1). Pairs that fit no group go to the anomaly
     group (C4);
   - flags two-sense pairs (C2);
   - runs a size check per group (C4);
   - marks every allocation provisional (C3).

   For M49, M67 and M83 the step first takes over the groups already in the tables (B5, section 3).
3. `cluster.validate` reports any M pair with no group, and any pair whose code has left its cluster.
   While a cluster has stale pairs, `reading.open` refuses it (C5).

**B. A work unit (0.C).**
4. A scope request goes subgroup → (code, surface) pairs → the `verse_lexical` rows that carry them.
   It is exact to the occurrence, and it never uses `word_strong` (S4).
5. The output JSON lists, for each verse, all of its occurrences: code, surface, subgroup, cluster,
   the two-sense flag and whether the occurrence is in the home group (S1+S2). The other subgroups are
   shown, to be read (S5). They don't add verses. T-coded occurrences come in as context (T-b).
6. A `qualifier` group is not opened as a home scope (E4).

**C. The reading.**
7. Each new node records the occurrence it reads (`verse_lexical.id`, S3).
8. The observe reading (`reading.record`) records what the verse says about each word: its role
   (RG-03) and its face (RG-09). It doesn't change any group. In the claims step (`reading.apply`),
   made from the tables (B:114), the flagged pairs are settled per verse and any pair move is decided,
   each with its reason (C2, C3; B4, section 2).
9. A T-coded word found to be the characteristic is added to the cluster and its subgroup, with the
   reason (T-a, rule 70). Step 3 then applies (C5).
10. Claims: duplication is grouped in `ib_observation` as it is today.

## 2. B4 explained: where a verse-level exception is kept

**What it is about.** The mapping works per pair: *ṭôb* rendered "please" goes to one group,
everywhere it occurs. Two rulings say that default is sometimes wrong for a single verse:

- **C2, two senses.** A flagged pair is "settled per occurrence in the reading". For example, *ṭôb*
  "please" defaults to S2 delight. In "if it pleases the king" the reading finds it is the king's
  will or favour, so in that verse it belongs to S4 favour.
- **C3, provisional.** "A reading may move a pair, with its reason."

So the reading produces a fact of the form "in this verse, this word belongs to group X, not the
pair's default". B4 asks where that fact is written.

**Why it matters.** The resolver needs it before it builds the next scope. If it isn't there, the
next scope on S4 favour misses "if it pleases the king", and the next scope on S2 delight still
brings the verse in under the wrong home.

**The options.**

| | a) a small table of exceptions, keyed by occurrence | b) on the node (`ib_node`) only |
|---|---|---|
| holds | occurrence (`verse_lexical.id`), the group it belongs to, reason, reading, when | the node's `cluster_subgroup_code` |
| resolver | reads the exception first, then the pair's default; one join | has to search the observations for any node that disagrees with the default |
| conflict | one row per occurrence, so one answer | several nodes on one occurrence can disagree, with no rule for which wins |
| without an observation | a settlement can be recorded even when no observation is written | needs an observation to exist |

A whole-pair move (C3: the reading finds the pair belongs elsewhere in every verse) is not an
exception. It changes the pair's row in `surface_subgroup` and keeps its old value in the change
record.

**My recommendation *(inferential)*:** a. The table stays small: one row only where a verse differs
from its pair's default.

**When it is written (v40).** The researcher asked whether this takes the first reading too far, into
the analytic work of the claims reading. It does, as v2 put it. Two things are done in different
places:

- **Recording the sense in a verse is the observe reading's work, and it is already required.**
  RG-03 gives each word its role in the verse, and RG-09 records its face, "where the sense departs
  from the general gloss". For "if it pleases the king" the observe reading records that *ṭôb* here
  is the king's will or favour. That needs nothing new.
- **Deciding the word therefore belongs to another group is analytic.** It is a classification made
  across the verses, from what was recorded. So it belongs in the claims step (`reading.apply`),
  which already settles each node's disposition from the tables (B:114). A whole-pair move (C3) is
  the same kind of decision and goes there too.

So the table in option a stays, but only `reading.apply` writes it, not `reading.record`. Until the
claims step has run, the occurrence stays in its pair's default group, with the two-sense flag shown
in the scope JSON. C2's wording, "settled per occurrence in the reading", is then read as "in the
claims step of the reading". That is your call (B4 in section 7).

## 3. B5 ruled: the existing subgroups are taken over

**The ruling (v38):** `cluster.subgroup` is retired and replaced by the surface subgroup routine. The
existing table data for M49, M67 and M83 is incorporated. A new run comes in only where that data is
in error or missing.

**What the tables hold (facts):**

| cluster | codes in cluster | codes placed in a subgroup | (code, surface) pairs | pairs placed | hits placed | subgroups |
|---|---|---|---|---|---|---|
| M49 Thanksgiving | 5 | 5 | 41 | 41 | 201 of 201 | 5 |
| M67 Sloth & Diligence | 11 | 9 | 44 | 24 | 37 of 74 | 4 |
| M83 Seeking & Inquiring | 7 | 7 | 104 | 104 | 539 of 539 | 4 |

- No placed code has left its cluster.
- M67 has two codes with no subgroup, and those are the data that is missing:
  - H5647I (work, labor, till, slaves and others; 32 hits);
  - H7423B (slack, slothful, idle; 5 hits).
- 1,847 nodes carry these subgroup codes (M49 745, M67 594, M83 508).

**How the incorporation works in the build *(inferential, follows the ruling)*:**
1. The 13 `cluster_subgroup` rows stay as they are: same ids, codes, labels, descriptions and anchor
   verses. They get `kind = group`. The 1,847 nodes stay valid with no change.
2. Each existing placement (code → subgroup) becomes one `surface_subgroup` row for every surface of
   that code, with `allocated_by = inherited`. That gives 169 pairs over the three clusters.
3. **Missing:** the 20 M67 pairs of H5647I and H7423B go through the new run, into the existing
   groups or the anomaly group.
4. **Error:** the old placement was made per code. In the session I check each inherited pair's
   surface against its subgroup's description. If one doesn't fit (for example a surface of a
   seeking code that reads as something else), it is moved with its reason, as a correction of the
   data. A move is never made for a better fit only. Every move is listed for the researcher in the
   pilot report.
5. `cluster.subgroup`, `cluster.reading` and `cluster.answer` are retired: their `cfg_step` rows are
   made inactive and `iba/app/ps/ClusterSubgroup.ps1` is archived. This meets #2275.

## 4. B6: the 606 nodes are not anomalies in the bucket's sense

**What they are (facts).** The 606 nodes are on 139 verses, 532 observations and 66 codes. In each of
those verses the same word, with the same rendering, occurs twice or more. For example, 1 Cor 7:27
has "seek" twice (G2212), and 1 Chr 28:4 has "chose" twice (H0977). The node names the code and the
surface, but not which of the two it reads.

**Why the bucket doesn't catch them.** The anomaly bucket (C4) holds **pairs** that fit no group.
These pairs map normally: both "seek"s in 1 Cor 7:27 are the same pair, so they go to the same
group. Nothing goes to the bucket. The open question is which **occurrence** was read, which matters
only for the per-occurrence reading record (S3).

**The options:**

| | |
|---|---|
| a) | put each on every matching occurrence: both "seek"s are marked read. One identical word in one verse, one group. |
| b) | list them in the anomaly bucket as a second kind, "node on more than one occurrence", and clear them by hand, as you assumed |
| c) | put each on the first occurrence by position. This is a guess (B:19), so it is not offered. |

**My recommendation *(inferential)*: b**, as you assumed: one bucket, with two kinds (pair, node),
both cleared by hand. Option a is quicker but would mark an occurrence read that the observation
may not have looked at, which is the #2262 mistake.
