## 1. Is the expectation realistic?

Yes, with one limit that cannot be coded away. The package already has the right shape: each `Read*` command writes an input packet with its instruction drawn from config, and each `Record*` command checks and writes. What it lacks is what forced the 37 interventions (`outputs/escalation/2637-manual-interventions-boast-boasting-v1-20261126.md`):

- packets too large to read whole
- an answer form that makes me compute ids, positions and nodes
- no check that lists every fault before recording
- recorder rules that are not stated in the packet

All of this can be built. The limit is that the judgements stay mine: which reading an occurrence belongs to, what a sense is, the text of an observation and the verse words it rests on. "Pre-coded" means judgement is the only thing I add; it does not mean no judgement.

What I will not claim: that one session finishes it. There are nine routines, about 94 refusal sites across four files (`iba/app/lib/layerreading.py`, `iba/app/lib/readcommands.py`, `iba/app/lib/layerinner.py`, `iba/app/lib/observationrecord.py`) to bring under config, and a test run per routine. I report progress routine by routine, each routine either passed under B:138 or open.

## 2. The contract every routine will meet

The routines are grouping, S1, 1.1, 1.2, 2.1, the sweep, the evidence validation, 3.1 and 3.2.

| Part | What the code does | What I do |
|---|---|---|
| Input packet | `Read*` writes the packet JSON and, beside it, a readable view (`.md`) of the same packet: the instruction, every rule the recorder enforces (by key and text from config), the data one item per line, and the allowed values of every answer field. A packet over its configured size is split into numbered parts by the code. | Read the view. |
| Output packet | The read writes an output form holding only the judgement fields, with every id, occurrence, older observation and allowed value already in place. | Fill the judgement fields. |
| Pre-check | A new `-Action CheckAnswer` runs every recorder check on the filled form and lists all faults at once, each with its rule key. It writes nothing. | Correct the form. |
| Processing | `Record*` builds everything else from the form (nodes, traces, coverage, ledger state), writes it, and advances the ledger. | Nothing. |
| Rules | Every refusal carries a rule key that exists in `cfg_method_rule` / `cfg_behaviour_rule` and is named in that read's instruction (`cfg_setting layer.read_types`). A test enumerates every refusal site and fails on a site with no key, or with a key the packet does not print. | Nothing. |
| Visibility | A cycle view per subgroup (`-Action Cycle`): each step, its input packet, its output packet, the record result, the refusals and the ledger state, in one file under the report path. | Read it; so can you. |

## 5. Decisions only you can make

1. **B2, grouping precedence.** The pull says a surface with no pair is a subgroup of its own; the seed rule says a word family stays together. boastful (base boast) met both. Options: (a) the word family wins: a surface sharing a base with another stays with it; (b) the no-pair rule wins, as was done ad hoc. My recommendation is (a), because the family rule is about meaning and the no-pair rule only about counts.
2. **G3, qualification at 3.1.** A qualification finding needs the qualifier word, a partner, but a 3.1 row may name only the subgroup's own occurrences. Options: (a) allow partner occurrences as nodes in 3.1 for a qualification only; (b) remove qualification from the 3.1 kinds, leaving it at 2.1. My recommendation is (a), because RG-04 defines qualification on both words.

One I will decide under B:98 unless you object: **C4, merge.** The instruction says merge is for an observation saying the same thing; the code takes only identical text. I will conform the code to the instruction: merge on the same meaning, with the surviving text the newer one and the older one recorded as merged.
