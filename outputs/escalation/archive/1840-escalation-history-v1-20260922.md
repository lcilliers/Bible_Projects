## #1840 — Same-strong repeat positions produce duplicate rows
type=issue source=researcher

**v1** (2026-09-22T17:03:56Z, Claude) state=raised next_action=review assigned_to=Researcher
> **short description (set this version):** Same-strong repeat positions produce duplicate rows
> **comment (set this version):** Found while verifying the M67 backfill (#1838): the M0.7/M0.8.1 exact-occurrence identity model (recordingpass.py, _is_strong_specific_occurrence_question's candidate matching) keys identity on (verse, strong) only -- it has no position/surface component. When the SAME Strong's code occurs at TWO DIFFERENT word positions within one verse (common for recurring function morphemes -- definite articles, prepositions, pronominal suffixes -- much rarer for M-code content words), the model correctly produces two distinct, position-specific findings, but the matching can't tell that apart from 'the same occurrence answered again' -- result: redundant duplicate rows, not data loss, but real noise. Confirmed concretely: Ezra.7.17's H9010 (definite article) occurs at position 6 (attached to bulls) and position 14 (attached to altar) -- two separate, correct observations, but stored as unmerged duplicates rather than one shared row citing both positions (the pattern M0.1/M0.5 word-level facts already use correctly).
> **context (set this version):** Scale: 109 of M67's 2560 expected (verse,strong,question) keys show this over-count pattern, concentrated in M0.8.1 (function-word-heavy population) and spread across many of the 35 verses, not just repeat-tested ones -- confirms this is a structural gap, not a session-testing artifact. No completeness impact (missing_count=1/2560, essentially complete) -- this is a data-quality/cleanliness finding, not a coverage failure. Root cause not fully traced to the exact code path (my reading of _existing_candidates suggests the SECOND occurrence's own candidate query should find the first as a match via the (strong,verse) pair-join, but empirically it doesn't merge) -- flagging the confirmed symptom and likely architectural cause rather than a guessed fix. Real design decision needed: should occurrence identity for these two question families become (verse, strong, position/surface) -- meaning genuinely different positions stay as separate rows, cleanly, by design -- or should M0.7/M0.8.1 instead consolidate all of a strong's occurrences within one verse into ONE shared observation citing every position (matching M0.1/M0.5's own pattern)? These have different implications for what 'the finding' means when the same code legitimately behaves differently at different positions in one verse. Not building either without your call, given #1832/#1834's own lesson this session about getting dedup identity wrong on the first attempt.
