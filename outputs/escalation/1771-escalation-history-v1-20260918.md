## #1771 — ib_observation.meaning_source has no write-time validation
type=issue source=researcher

**v1** (2026-09-18T14:36:12Z, Claude) state=raised next_action=review assigned_to=Researcher
> **short description (set this version):** ib_observation.meaning_source has no write-time validation
> **comment (set this version):** Researcher's own observation, spotted browsing a raw query result: meaning_source values don't look enum-driven, 'not very useful as a lookup.' Confirmed live: cfg_enum ib_observation.meaning_source IS registered with exactly the 3 values the column's own cfg_column.use text documents (strong_meaning_tree, strong_lexicon.lsj, strong_lexicon.mounce) -- but recordingpass.py has NO _validate_meaning_source gate (unlike tag/question_code/obs_text, which each have one). 42 distinct free-text values live in the data: every separator style mixed together (+, ' + ', '; '), every naming variant (lsj vs strong_lexicon.lsj, mounce vs strong_lexicon.mounce), every ordering permutation of the same 3-source combination, plus values that don't belong in this column's documented vocabulary at all (role list/role tags, cluster_codes, cluster.cluster_code, verse_reading_observations, char_subgroup_observations, char_reading_observations, n/a).
> **context (set this version):** Not a mechanical one-line fix like #1769's regex broadening -- a real design decision first: (1) is a MULTI-source combination (e.g. an observation legitimately drawing on 2-3 sources at once) meant to be representable at all, or should meaning_source always name exactly one primary source? If combinations are legitimate, what's the canonical separator/format (today's data shows +, ' + ', and '; ' all used interchangeably for the identical semantic combination)? (2) the non-enum values found (role list, cluster_codes, verse_reading_observations, etc.) suggest meaning_source is ALSO being used, in some observations, to answer a genuinely different question ('which prior ib_observation category grounded this' rather than 'which of the 3 meaning tables') -- worth deciding whether that's a real second use this column should formally support (a second enum group, or a separate column) or a drift that should be corrected back to the documented 3-value vocabulary only. (3) once the target vocabulary/format is decided, needs both a write-time validation gate (same shape as _validate_tag/_validate_question_code/_validate_obs_text) AND a one-time backfill/normalization migration for the 42 existing variants -- not just gating new writes while leaving live data messy. Not built this turn.
