**v2** (2026-09-06T05:35:49Z, Claude) state=re-assigned next_action=ready_for_approval assigned_to=Researcher
> **comment (set this version):** Root cause found in code, not just inferred from data -- confirms and sharpens both your framing and my initial hypothesis. See resolution.
> **resolution (set this version):** Read iba/app/lib/lexical.py:resolve_code() directly. Two compounding defects, both real: (1) SIZE/WEIGHT (your framing, verbatim: 'carries an enormous weight that is not part of the definition'). Every resolved_sense value, on EVERY row, in BOTH code paths (line 198 no-sense-rows fallback, line 213 the normal narrowed path), is built as f'stepGloss: {full raw dictionary text}' -- either alone, or with the actual narrowed/selected sense appended after an em-dash. The complete raw stepGloss entry (which is a corpus-wide constant per code, not per-occurrence) gets duplicated into every single row that uses that code, corpus-wide. That is the actual, root, mechanical cause of the size problem #1526 surfaced (51MB/75,350 rows for M42) -- not an encoding-verbosity issue, a genuine per-row duplication of constant data the schema didn't need to store per-row at all. (2) LOGICAL DEFECT in gloss_consistent_in_verse (deeper than first reported): resolved_sense, as computed, is a PURE FUNCTION of (strong, morph_code) alone -- nothing in resolve_code() reads the verse, the surrounding words, or any other per-occurrence context. gloss_consistent_in_verse groups rows by that EXACT SAME (strong, morph_code) key and checks whether resolved_sense differs within a verse. Since resolved_sense is mechanically determined entirely by the grouping key itself, this check is tautological -- it is mathematically guaranteed to read 1 for every row, for any corpus, under the current implementation. It is not a rare-case bug or a coincidence that Dan 1:8 H0834A reads 1 instead of the spec's expected 0 -- the check cannot ever produce anything but 1, structurally, until resolved_sense itself incorporates something that actually varies by occurrence/context (which per the windows-register documentation is exactly the kind of thing that needs a real per-verse READ, i.e. arguably Window 2's job, not a mechanical Layer-1 column at all). Recommends: (a) stop embedding the full stepGloss text per-row -- store/derive it once per code (already exists corpus-wide in the strong table itself) and reference it, or drop it from resolved_sense entirely, keeping only the narrowed/selected text; (b) either retire gloss_consistent_in_verse as a dead/tautological check, or redesign resolved_sense to actually incorporate a real per-occurrence signal before the check can mean anything. Neither applied -- flagging for your decision, this touches a documented Layer 1 mechanism (#1383 spec) and a live corpus-wide column (544,572 rows).
