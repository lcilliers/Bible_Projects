# #2212 — Prose patches name a retired apply script: decision

Researcher, chat 2026-10-23 (verbatim): "#2212 should be easy to complete and close"

## What is the case (checked 2026-10-23)

- Three prose steps are **active** in `cfg_step` (inactive = 0) and write a `PROSE` patch file
  rather than a row: `prose.import_chapter` (ImportChapter: import an edited chapter),
  `prose.set_status` (SetStatus: set a section's status) and `prose.flag_fix_apply`
  (FlagFixApply: apply a find-and-replace fix to the chosen sections).
- The script that applied a `PROSE` patch, `scripts/archive/apply_session_patch.py`, was set
  inactive and moved to the archive on 2026-10-22 (#2207, BUILD.md sec 377), under the
  researcher's ruling of 2026-08-18 on #729 (BUILD.md sec 151, verbatim): *"set these 110 module
  to inactive. if the time arise when they need to be used, then the script can be updated to be
  fully compliant"*.
- So a patch can be produced, but nothing live applies it. `iba/app/USER-GUIDE.md` sec 11 says so
  and points here. These still tell the user to apply with the retired script:
  `iba/app/handlers/prose.py` (lines 4, 79, 120, 143), `iba/app/ps/Prose.ps1` (lines 20, 25) and
  `iba/app/lib/prosestore.py` (lines 10, 663).
- Config still depends on these steps:
  - `cfg_setting governance.prose_canonical_authority` says chapter review status is set per
    section through `Prose.ps1 -Step SetStatus`.
  - `cfg_behaviour_rule` B:85 (prose-only-on-instruction) says the prose is the researcher's,
    built up as each area of focus develops.
- The last prose write in `bible_research.db`: `record_change_log` max `change_datetime`
  2026-09-18T05:36:39Z (1,287 rows); `prose_section` newest `created_at` 2026-09-05T05:29:31Z.

So "complete and close" needs a decision first: either prose patches are applied again, or they
are no longer produced.

## Options

**A. Bring the apply back as a compliant app step.** This is the #729 ruling's own route
("updated to be fully compliant"). The apply logic moves into the app as a registered step
(e.g. `prose.apply_patch`, `Prose.ps1 -Step ApplyPatch -PatchFile … [-DryRun]`), dispatched
through `iba/app/run.py`, with its `cfg_step` / `cfg_utility` rows. It keeps the existing
`cfg_write_grant` writer `apply_session_patch`, the `record_change_log` choke point
(B:48 to B:50) and the two-patch ordering (B:53). The three steps' messages,
`iba/app/USER-GUIDE.md` sec 11 and the flag-fix cycle then name it.
Cost: a build (code, config rows, tests on a copy, a BUILD.md entry), in Developer Mode.

**B. Stop producing prose patches until a prose edit is needed.** Set `prose.import_chapter`,
`prose.set_status` and `prose.flag_fix_apply` inactive. Remove them and the flag-fix cycle's apply
steps from `iba/app/USER-GUIDE.md` sec 11 and `iba/app/ps/Prose.ps1`. Rewrite
`governance.prose_canonical_authority`, since the SetStatus route it names would be gone.
Extract, Search, ExportChapter, Flag and FlagFixPropose stay. A later prose edit is raised as its
own item, and A is built then.
Cost: three `cfg_step` rows, one governance setting and two documents. Still Developer Mode.

**Recommendation:** A. Under B:85 the prose grows as each area develops, and the governance
setting relies on SetStatus, so prose writes are part of the standing process. B would also
mean rewriting a governance setting only to undo it later. B is smaller, and is the choice if no
prose edit is expected soon (none has happened since 2026-09-18).
