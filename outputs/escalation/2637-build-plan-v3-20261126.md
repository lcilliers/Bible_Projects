## 1. Is the expectation realistic?

Yes, with one limit that cannot be coded away. The package already has the right shape: each `Read*` command writes an input packet with its instruction drawn from config, and each `Record*` command checks and writes. What it lacks is what forced the 37 interventions (`outputs/escalation/2637-manual-interventions-boast-boasting-v1-20261126.md`):

- packets too large to read whole
- an answer form that makes me compute ids, positions and nodes
- no check that lists every fault before recording
- recorder rules that are not stated in the packet

All of this can be built. The limit is that the judgements stay mine: which reading an occurrence belongs to, what a sense is, the text of an observation and the verse words it rests on. "Pre-coded" means judgement is the only thing I add; it does not mean no judgement.

This build takes more than one development session. That is for your information, not something you must mitigate. It refers to the Developer Mode sessions that build the code, not to the standard sessions that will run it. It is doable. There are nine routines, about 94 refusal sites across four files (`iba/app/lib/layerreading.py`, `iba/app/lib/readcommands.py`, `iba/app/lib/layerinner.py`, `iba/app/lib/observationrecord.py`) to bring under config, and a test run per routine. Progress is kept on #2637 routine by routine, each routine either passed under B:138 or open, so a later Developer Mode session continues from the record. The only thing asked of you is to start each one in Developer Mode until #2637 says every routine has passed.

The routines are grouping, S1, 1.1, 1.2, 2.1, the sweep, the evidence validation, 3.1 and 3.2.

| Visibility | A cycle view per subgroup (`-Action Cycle`): each step, its input packet, its output packet, the record result, the refusals and the ledger state, in one file under the report path. | Read it; so can you. |

## 5. Decisions

- **G3, qualification at 3.1, decided by you.** Your words: "qualifiers enhance or describe the working of the behaviour. It should not be ignored, or be set aside without due consideration. Not all qualifiers applies nor have an impact on the behaviour and these qualifiers does not have to be forced into the analysis and reading. This usually would be subject the judgement and reading." In code: a 3.1 qualification finding may hold the qualifier's occurrences (partner words) as nodes, with the role qualifier, where the reader judges the qualifier bears on the working. The 3.1 packet lists every qualifier found at 2.1 for the subgroup. Each one is either used by a finding or declared not bearing on the working with its reason. None is demanded into a finding, and none is dropped without its reason. RG-04 and IB-02 are amended in config to say so.
- **B2, grouping precedence.** There is no conflict to decide. The no-pair rule of GP-01 (`cfg_method_rule`) applies only to a surface WordNet does not hold, and boastful is in WordNet; for it, the word family is the default, and GP-04 allows a separate subgroup only with a stated difference in kind of meaning. Whether boastful's stated difference is enough is a reading judgement for the standard session. In code: the grouping packet prints GP-01 and GP-04, and CheckAnswer lists every subgroup split from its word family, with the difference it states, for that judgement to be confirmed.
- **C4, merge.** The instruction says merge is for an observation saying the same thing; the code takes only identical text. I conform the code to the instruction (B:98): merge on the same meaning, with the surviving text the newer one and the older one recorded as merged.
