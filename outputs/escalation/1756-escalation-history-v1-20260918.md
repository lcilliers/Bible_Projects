> **context (set this version):** Scope as instructed: (1) a batch/step-level control table -- one row per batch/chunk of a live multi-batch run, written at batch START (before the API call) and updated at batch END (after record_batch commits), carrying at minimum: run_id, work_package/step, selector (cluster_code/subgroup_code/etc.), batch/chunk ordinal, started_at, ended_at, status (running/committed/failed), and whatever identifies exactly which verses/items that batch covered (so a resume can compute what's NOT yet covered, not just 'batch N of M' by position -- the selector's own item list could in principle change between runs, e.g. cluster_strong reassignment, so resume-by-content is safer than resume-by-position alone). (2) Resume/skip: every live multi-batch step (lexical.meaning today; cluster.subgroup/cluster.reading/cluster.answer are single-call-per-run so less exposed, but should use the same table for consistency and crash visibility) checks this table before each batch and skips any batch already committed for this run/resume lineage, rather than blindly restarting from batch 1. (3) Crash safeguard: same table is the mechanism for detecting a run that died mid-batch (a 'running' row with no matching 'committed'/'failed' terminal row) so a resume can tell a genuinely-interrupted run from a fresh one. (4) Progress monitor: the researcher can read this table live, mid-run, to see how far a long batch run has gotten without waiting for it to finish or reading a background process's raw stdout -- exact query/report shape (a PS script? a Reports.ps1 addition? read via the SQLite extension directly?) is an open design question, not specified by the researcher's instruction, Claude's own call to make in the design. This is real design/build work, not a mechanical fix -- per governance.module_utility_test_plan a test plan is required, per governance.tables/governance.table_columns any new table+columns need cfg_table/cfg_column registration, and per governance.module.config it likely needs its own cfg_* control (at minimum which steps use it). > **resolution (set this version):** DESIGN PROPOSAL. New table run_batch: id PK, run_id, work_package, step, selector_key (e.g. cluster_code, or cluster_code|subgroup_code), batch_ordinal, batch_content_key (stable hash of the sorted verse_id/item-id list that batch actually covers -- content-keyed, not just position-keyed, so resume is correct even if the selector's own item list shifts between runs, e.g. a cluster_strong reassignment), status (running|committed|failed, new cfg_enum), started_at, ended_at, error_message, cost_usd. UNIQUE(step, selector_key, batch_content_key) -- deliberately NOT scoped to one run_id, so a brand-new run_id can still see and skip a batch a PRIOR run_id already committed; that's the whole resume/skip mechanism. Write pattern per batch, inside the handler's existing loop: (1) before the API call, check run_batch for a 'committed' row matching (step, selector_key, this batch's content_key) -- if found, skip the batch entirely, no API call, log the skip in the run's own outcome message; (2) if not found, INSERT status='running', started_at=now, commit immediately (so a crash mid-batch leaves this row visible, and a monitor query sees it live); (3) call the API, record_batch, commit as today; (4) UPDATE the same row to status='committed', ended_at=now, cost_usd=real_cost, commit. Any exception between (2) and (4) is caught, the row UPDATEd to status='failed'/error_message before re-raising -- this IS the crash safeguard: a 'running' row with no terminal update is unambiguous evidence of a dead run, distinct from one that simply hasn't reached that batch yet. Monitor: new read-only script BatchProgress.ps1 (-RunId or -Step/-Selector) querying run_batch for live counts (committed/running/failed, latest batch, elapsed) -- doesn't fit Reports.ps1's existing word-scoped shape, so a new small script rather than bolted onto that one. Integration: lexical.meaning (verse-reading) first -- the one with proven pain this session; cluster.subgroup/cluster.reading/cluster.answer are single-call-per-run today (lower priority) but should still write one row each for crash-visibility/monitor consistency. Governance: needs cfg_table + cfg_column entries for run_batch (governance.tables/table_columns), a cfg_enum for status, and a test plan per governance.module_utility_test_plan covering (a) skip-on-already-committed, (b) a simulated crash mid-batch leaves a running row and the next invocation detects + resumes past only the genuinely-committed batches, (c) BatchProgress.ps1 returns accurate counts against a run still in progress. Open question for your call: keep run_batch generic across every live multi-batch step (my recommendation, one shared mechanism) vs a bespoke table per step -- proposal above assumes generic/shared.
