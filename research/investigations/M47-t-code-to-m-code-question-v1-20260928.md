# M47 — do the T-coded inner-being terms matter, and should they be re-coded? (v1)

**Date:** 2026-09-28
**Status:** answer + recommendation. **Nothing changed in any table.** Read-only checks against `iba/app/db/iba.db`.
**Question (researcher, verbatim):** "Does it matter that some terms are currently in T-codes, and should be in M-codes. Would it make sense for you to run through the M47 work and prepare a json that can be handed to VS code to update all the tables. Is there a risk that it would negatively impact any work already done?"
**Companion:** `M47-seat-coverage-and-unseated-verses-v1-20260928.md` (same folder).

---

## 1. Does it matter? — Yes

Every M-cluster reading, M47 included, sees only M-coded words. **An inner-being term filed in a T-code is invisible to that reading.** The M47 work has already run into this:

| Term | Strong's | Now in | Verses | Where it showed up |
|---|---|---|---|---|
| die | H4191, G0599 | T3 Operations | 699 + 99 | G §0.2: "Life & Death" shows only the life side |
| death | H4194, G2288 | T10 Places [sic] | 151 + 106 | same |
| say (the "said in his heart" series) | H0559 | T3; **confidence low, review_flag = 1** ("cluster undetermined") | 4,340 | B §0; depiction §2.1c |
| within / inward parts (*qereb*) | H7130G | T14 Body-Parts | 194 | seat-coverage §2: an unnamed seat |
| bone | H6106G | T14 | 88 | ruling 4 (excluded as a study word) |
| kidneys | H3629 | **T2 Supplementary** (catch-all) | 26 | ruling 4 |
| bowels ("belly") | H4578 | T2 | 30 | ruling 4 |
| belly / womb | H0990G/H/J, H7358 | T2 | 16 + 45 + 9 + 25 | — |
| affection / entrails (*splanchna*) | G4698 | T2 | 11 | — |

**Two facts shape the answer:**
1. **A word can carry an M-code and a T-code at the same time.** Precedent: "face: anger" (H0639G) is live in **M02 and T14**, verse-checked 2026-09-08. So the fix need not be "move T → M". It can be "**add** an M-row and keep the T-row", which keeps its body-part or operation role intact.
2. **Some terms are inner-being only in some uses.** "say" (4,340 verses) is inner-being only in "said in his heart". "die" is a life-and-death state; whether it belongs in M25 is a judgement about the cluster. Coding every occurrence of "say" into an M-cluster would flood it. For terms like these, the better tool may be to **include the T-code in the M47 angle** (as the seat-coverage proposal suggests) rather than re-code the word.

## 2. Would a JSON update spec make sense? — Yes, with conditions

It fits the app's own conventions. Each condition below is taken from how earlier reassignments were done (e.g. `reclassify_g0627_to_t3_v1_20260917.py`, escalation #1598):

- **One JSON spec, one line per term**, with: strong, current code(s), action (`add_m` / `move` / `leave` / `handle_as_cooccurrence`), target code, evidence (M47 file §), and **`"approved": false` until you mark it** ([[feedback_remediation_stop_points]]).
- **Applied by a migration script**, not by hand edits:
  - soft-delete-and-insert, never an edit in place
  - rationale quoting your instruction verbatim, plus an escalation id
  - `--dry-run` first; idempotent
  - a `BUILD.md` entry
- **`verse_lexical.role` must be refreshed afterwards.** `role` is a snapshot of `cluster_strong` taken at build time. The code already has a stale-role detector (`lib/lexical.py` `stale_role_strongs_for_cluster`). Without the refresh, every verse-level count — including the seat-coverage table — would silently use the old assignment.
- **VS Code or here:** the spec can be handed to VS Code as you suggest. I can also apply it in this environment by the same route. Either way, the spec is the reviewable object.
- **Scope:** besides the T → M terms above, Batches A–E recorded M → M misfiles in their §0/§R (for example "declares the Lord", H1696, sitting in M42 Prayer). These could go in the same spec as `leave` or `move`, for you to decide. They were kept as a record, not as rulings.

## 3. Is there a risk to work already done? — Low, if sequenced correctly

| Item | Risk | Evidence |
|---|---|---|
| Observations and nodes | **None found** | 0 `ib_observation` rows and 0 `ib_node` rows reference any of the 14 candidate Strong's codes |
| Batch files A–H | **Not overwritten; become incomplete** | They are static `.md` files built on the 2026-09-27 CSV snapshot. New M-coded terms would add pairs they never saw → a **delta revisit** (read only the new pairs), not a rerun |
| M47 input CSVs | Stale after the change | Regenerate the surface and pairs files, and diff old against new |
| Seat-coverage numbers | Would change | They are regenerated by script; no reading has been done on them yet |
| Cluster status | Membership changes after "assignment completed" | All affected clusters (M25, M47, M02 …) are at `t_cluster_assignment_completed`. Adding members to a closed assignment is a verse-level change ([[feedback_verse_change_revalidation]]) — record it; any cluster whose findings rest on the old membership is revisited |
| Role snapshot | Real risk if skipped | See §2 — refresh is mandatory |

**The main risk is order.** If the re-coding comes *after* the seat-coverage tie-profile and the pilot reading, those have to be redone. It should come **before** them.

## 4. Recommended sequence

1. **I draft the candidate list** — this table extended with anything else the M47 files flagged — as an `.md` for your mark-up, plus the matching JSON spec with `approved: false` throughout.
2. **You decide per term:** add M-row / move / leave / handle as co-occurrence. Also decide whether M47 itself should gain the body-seat words (*qereb*, kidneys, bowels, *splanchna*), which would reverse ruling 4 for the co-occurrence angle.
3. **Apply** (VS Code or here): dry-run → live → role refresh → `BUILD.md` → escalation record.
4. **Regenerate the M47 inputs**, diff them, and revisit Batches A–H for the delta only.
5. **Then** run the seat-coverage tie-profile (Step 1) and the pilot.
