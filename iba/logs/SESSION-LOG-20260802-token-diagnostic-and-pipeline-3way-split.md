# Session Log — 2026-08-02 — Token-consumption diagnostic, follow-up architecture review, and the book-by-book pipeline split into 3 module entry points

## Task

Researcher opened the session flagging that Hosea's completion (book 6, previous session,
2026-07-30) "turned out to be very intense and consumed a large chunk of tokens," suspected this
was related to streaming a whole book without clearing context, and wanted the method's three
implicit phases (prepare data, debate, narrative) separated so token consumption and quality could
be controlled independently. The session moved through three stages: (1) diagnose exactly what
consumed the tokens and why it spiked, (2) evaluate (and largely set aside) a database
element-first redesign as the fix, (3) build the actual fix — a 3-way pipeline split plus a
session-pacing guideline.

## What was found — the diagnostic

Full detail: [`iba/app/reports/token-consumption-diagnostic-20260802.md`](../app/reports/token-consumption-diagnostic-20260802.md).

- **Not the narrative-generate API spend** — that is a separate, real-USD-metered pool
  (`ANTHROPIC_API_KEY`, logged to `narrative-generate-usage.csv`), unrelated to the Claude Code
  subscription's daily/weekly caps that were actually exhausted.
- **Calibrated a real chars-per-token ratio** (≈2.92) from one hard data point — Hosea's own
  narrative-generate call's measured 231,610 input tokens against its known-size assembled
  package — then applied it to file sizes across the pipeline, since no per-turn token telemetry
  is available from inside Claude Code itself.
- **The real driver: Micah (7 ch) and Hosea (14 ch) ran full end-to-end back to back in one
  unbroken conversation the same day** (git history: 11:09 → 17:29, ~6h20m), on top of a morning
  building new pipeline code (`report.book_narrative_generate` itself). ≈1.13M tokens of raw
  extract-reads and debate-writes moved through one continuous context, with no context-clearing
  checkpoint anywhere in that stretch — compounded further because every later turn in an
  unbroken conversation still carries the full accumulated history of every earlier one.

## Follow-up — the element-first DB redesign question, and why it was set aside

Researcher's next question: since the debate `.md` files are mechanically assembled and reread by
`report.whole_book_read`/`report.book_narrative_generate`, would storing each analytical element
in the DB and assembling documents only from what's needed be more efficient? Investigated against
live code, not reasoned abstractly:

- Confirmed **`report.verse_span_meaning` is already a pure rendered view** over normalized DB
  tables (`verse`/`span`/`strong`/`strong_meaning_parsed` etc., `versespanmeaningreport.py`) — no
  new table needed there.
- Confirmed the debate content itself (Observation/Operation/Interrogative/Decision) exists **only**
  as free text in `.md` files — `passage` tracks paths/status only — and that
  `wholebookread.py`/`narrativegenerate.py` do re-read/re-parse those files wholesale
  (`narrativegenerate.py:90-125`'s `gather_book`/`assemble_package` reads full raw text verbatim).
- **But this reading happens inside dispatched Python scripts, never through this conversation's
  own `Read` tool** — so the "recycling" costs real narrative-generate API dollars (a genuine,
  separate, smaller inefficiency), not the Claude Code cap that actually caused the incident. An
  element-first redesign would not have prevented Micah/Hosea's cap exhaustion, because the debate
  content still has to be read from source and generated by an AI exactly once regardless of
  storage format — verified and stated plainly rather than left as an appealing-sounding but
  untested assumption.
- Researcher agreed to set this aside rather than prolong it: "let me not prolong this debate for
  settling to token issue."

## What was built — the pipeline split

Full detail: `BUILD.md` §54, `GOVERNANCE.md` §31.

Per the researcher's direct instruction ("Change the config to ensure that the rules for each of
these modules are adequately separated and that I have three separate ps module entry points"):

1. `passage.debate_session_chapter_guideline` (`cfg_setting`, value `3`) — the advisory
   session-pacing rule, recorded as config per `governance.rules_must_be_config_driven`, not
   code-enforced (the debate-fill step is never dispatched through `run.py`, so nothing can gate
   on it).
2. New chained work package `chapter-generate` (`Chapter-Generate.ps1`) — `report.verse_span_meaning`
   + `report.passage_debate`, one call, both handlers reused unchanged.
3. New chained work package `book-narrative` (`Book-Narrative.ps1`) — `report.book_narrative_generate`
   + `report.book_narrative_validate`, one call, bespoke orchestration feeding generate's own
   output path into validate automatically.
4. `report.whole_book_read` — unchanged, already its own separate entry point.

All 7 changes went through `configmaint.propose` → `Escalation.ps1 -Action AnswerRun -Decision
Approve` → re-run to apply (escalations #416-422), per governance's approval-gated path — no
direct `cfg_*` writes.

**The plan was corrected live by `configmaint.validate` itself, not assumed correct.** The
original plan (discussed and confirmed in chat) kept the four old standalone work packages active
as recovery tools alongside the three new ones. Applying that, then actually running
`configmaint.validate`, failed hard (`report-stop`): step names must be globally unique across
work packages (`escalation`/`cfg_on_fail` match on `step` alone) — a real, previously-established
rule (§24), not a style preference. Fixed by retiring (`inactive=1`) the four old work packages and
their now-duplicate `cfg_step` rows (8 more governed changes, escalations #423-431) — which also
gave the researcher's "exactly 3 entry points" ask more cleanly than the original plan would have.

A resulting known-limitation finding (`find_filled_by_referencing_inactive_step` flagging 6
`passage.*` columns as "stale," because it checks for any inactive row under a step name rather
than whether an active one exists elsewhere too) was reviewed, confirmed as a false positive, and
answered on the validation escalation with that reasoning recorded (#432/#433) — not silently
dismissed.

**Verified before calling it done:** both new `.ps1` files parse clean; `Cfg().sequence()` resolves
both new work packages to their exact expected 2-step orderings; `configmaint.validate` returns
`ok` clean on the live store. Not yet run end-to-end against a real book.
