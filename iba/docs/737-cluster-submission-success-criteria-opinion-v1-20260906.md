# What matters most for a cluster's successful submission into a Window 2 analysis run

- **status:** Opinion / judgement call, asked for directly. Not a finding, not something derived

---

## Ranked, with why

**1. Membership settledness — no open dispute about who's even in the cluster.**
This is the actual precondition, not a nice-to-have, because everything downstream is *derived*
from membership: the verse-set (Step 1), the catalogue findings, all of it. If a cluster's own
composition is still contested — M10b/M10c/M27's unresolved 2026-08-13 relocation is the live
example — a finding produced today and tagged "M27" may be sitting on the wrong 20% of its members
next month, and there's no way to tell which findings are affected without redoing the read. Every
other criterion below is worth nothing if this one is wrong, because the fix isn't a patch, it's a
redo. This is why I'd rank it above content-quality: a cluster with mediocre but *settled*
membership is submittable; a cluster with excellent-looking membership that's still mid-dispute is
not.

**2. A content-quality signal good enough to trust the read that's about to happen — not perfection, a floor.**
Nobody is proposing to hand-verify every strong before submission (that's the bulk-work trap the
on-demand strategy exists to avoid). But the provenance data in #1525's Appendix B is a real,
already-available signal, and it varies enormously — M27 is 56% medium/high confidence with zero
`review_flag`s; the 37 clusters M48–M84 are 100% one unverified mechanical pass from yesterday. I
think it matters which of those two kinds of cluster gets submitted *first*, because the first
submission is also the one that tests the process itself — a bad read caused by bad membership
looks, from the outside, identical to a bad read caused by a flawed *process*, and the two need to
be told apart. Submitting a well-provenanced cluster first isolates the process as the variable.

**3. Size proportionate to what can actually be read with sustained attention.**
You've said directly, twice now (Layer 2 strategy, and implicitly in the "no bulk work" framing):
AI's quality and consistency degrade on large repetitive tasks. A cluster's verse-set size is not
a neutral fact under that constraint — M65 (3,092 verses) submitted as one unit is a different risk
profile than M32 (Covenant, tiny and fully manual) or M67 (14 verses). I don't think "small is
always better" — a cluster too small to have real texture isn't a useful first test either — but I
do think size deserves to be a submission-time decision, not an afterthought: either pick a
moderate-sized cluster first, or explicitly decide how a large cluster gets sub-batched without
that becoming, in practice, the same bulk-repetition problem in disguise.

**4. The catalogue's HIB-relevant question set is fixed before the read starts, not decided mid-stream.**
This is more a readiness-of-the-*process* criterion than a property of any one cluster, but it
gates every cluster equally: if "which questions are we even answering" is still open (escalation
#1524), the first submission can't be evaluated against anything stable, and its output tells you
less about whether the *cluster* was ready than about whether the *rubric* was. I'd want this
settled, at least provisionally, before the first cluster goes in — not necessarily exhaustively
(the earmarking pass is bounded and small now, per #737's correction), but fixed enough that the
debate step has a real target.

**5. The process disciplines are actually being followed, not just described.**
Full verse + all its phenomena, never a subset; look backward/forward for context when needed;
unresolved recorded as a finding, not silently dropped. These are properties of *how the read is
conducted*, not of the cluster itself, so I've ranked this last — but a "successful submission"
that skipped any of these wouldn't be successful regardless of how clean the cluster's membership
was going in. It belongs in the definition of success, just not as a gating criterion for *which*
cluster to pick.

## What I'd actually do with this, if asked

Not decided here, offered only because the ranking implies it: of the 85 clusters, **M27** looks
like the strongest first-exemplar candidate on the data in hand — settled membership (no known
open dispute, unlike its own near-neighbours M10b/M10c), the best confidence mix of any
substantial cluster (56% medium/high, zero `review_flag`s), and a moderate size (48 strongs, 591
verses per #737's earlier report) that's neither trivial nor unmanageably large. That's a
recommendation, not a decision — yours to take, reject, or ask me to re-argue against a different
candidate.
