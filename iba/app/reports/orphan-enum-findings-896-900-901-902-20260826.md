## b) The validation check, and why each one fails it

**The check** (`find_orphan_configs`, `iba/app/lib/cfgquality.py:125`, run for every `cfg_enum`
group): a group counts as "used" only if its own `name` appears, anywhere in the live `.py`/`.ps1`
corpus (excluding `iba/app/migration/`, which only ever *writes* a value, not applies it), as a
literal argument to `.enum(` or as `name="..."`/`name='...'` in a raw SQL `WHERE` clause. There is
one documented escape hatch: if `cfg_column.expectation` is set to `enum.<name>` on the column the
group is meant to police, `lib/valuequality.py`'s own engine enforces it *data-driven*, and the
check exempts that group from needing a literal call site at all (the same mechanism a
`cfg_setting`'s `pattern:<key>` expectation uses).

**Checked live, not assumed: none of the 7 backing columns has `expectation` set.**

| Group | Backing column | `expectation` | Literal `.enum(...)`/`WHERE name=...` call site? |
|---|---|---|---|
| `prose_section_status` | `prose_section.status` | `NULL` | none found |
| `prose_section_author` | `prose_section.author` | `NULL` | none found |
| `prose_section_type_source_stage` | `prose_section_type.source_stage` | `NULL` | none found |
| `prose_section_type_lifecycle_tag` | `prose_section_type.lifecycle_tag` | `NULL` | none found |
| `prose_section_type_book_label` | `prose_section_type.book_label` | `NULL` | none found |
| `record_change_log_change_type` | `record_change_log.change_type` | `NULL` | none found |
| `record_change_log_status` | `record_change_log.status` | `NULL` | none found |

That's the mechanical reason all 7 fail identically. **But the 7 are not actually the same kind of
gap** — checked the live schema directly (`bible_research.db`, `PRAGMA`/`sqlite_master.sql`), not
just the config metadata's own claims:

| Group | Real DB `CHECK` constraint enforcing it? | What this means |
|---|---|---|
| `prose_section_status` | **Yes** — `CHECK (status IN ('draft','in_review','approved','archived'))` | The enum accurately *documents* a real, enforced constraint. Nothing wrong at runtime; only the config-code cross-reference is invisible to this checker. |
| `prose_section_author` | **Yes** — `CHECK (author IN ('claude_ai','claude_code','researcher'))` | Same as above. |
| `record_change_log_change_type` | **Yes** — `CHECK (change_type IN ('insert','change','delete'))` | Same as above. |
| `record_change_log_status` | **Yes** — `CHECK (status IN ('change_proposed','change_applied','declined'))` | Same as above. |
| `prose_section_type_source_stage` | **No** — `source_stage TEXT NOT NULL`, no `CHECK`, no `FK` | The enum documents an *intended* vocabulary that is enforced **nowhere at all** — not by config, not by code, not by the database. Confirmed by the column's own `cfg_column.use` text, written independently at build time: *"Uncontrolled: no CHECK or FK constrains the eleven values in use."* |
| `prose_section_type_lifecycle_tag` | **No** — `lifecycle_tag TEXT`, no `CHECK` | Same — unenforced anywhere. |
| `prose_section_type_book_label` | **No** — `book_label TEXT`, no `CHECK` | Same — unenforced anywhere. |

**This is the real finding the automated check can't see, because it only asks "is this read by
name," not "is this enforced by anything."** 4 of the 7 are misleadingly labelled — they read as
identical advisory findings to 3 that are materially different: a bad `status`/`author`/
`change_type`/`change_log.status` value is structurally impossible today (SQLite refuses the
write); a bad `source_stage`/`lifecycle_tag`/`book_label` value is not just unread by config, it's
**accepted silently by the database and the application both**.

## Precedent — why this was ever left this way

`record_change_log`'s 2 groups were accepted as a standing advisory at escalation #838
("CHECK-only enforcement accepted for now") — i.e. the researcher already decided, once, that
"the `CHECK` constraint is real enforcement; the `cfg_enum` row is a documentation convenience, and
it's fine for the orphan-check to keep flagging it rather than wiring `expectation`." #829's build
extended the identical treatment to the 5 new prose groups without re-litigating it (`BUILD.md`
§176: *"same shape the researcher already accepted... applied to this round's 5 new instances"*).
**That precedent genuinely covers 4 of the 7** (the `CHECK`-backed ones) — it does **not** cover
the 3 `prose_section_type` groups, which have no `CHECK` to fall back on and were never
individually distinguished from the other 4 when the "accept as advisory" disposition was applied.
