**Base (prepare raw for lexical analysis)**

## What it configures

THE PREPARATION STAGE. Process raw into the substrate the lexical read needs — the span master, the stem master, the char seed, and passages — and hand it over under signoff. Everything here is mechanical: derivation, never judgement.

- `process` — The stage's rules — what it derives, in what order, and the signoff that ends it.
- `entities` — What it owns: the span master, the stem master, the candidate seed, passages.
- `output` — The base review pack — what the researcher signs off.
- `validation` — The gates, including the signoff gate that releases lexical.

**4 open question(s)**

- **`open.base.signoff-mechanism`** — The signoff is a HUMAN gate — the only one in the pipeline so far. How is it recorded, what is its scope, and what invalidates it?
  - _recommendation:_ Per book; recorded with who/when/cfg_version + a hash of the base outputs it covers; AUTO-VOIDED when any input beneath it changes. The hash is what makes invalidation mechanical rather than remembered — the researcher signs off on a specific state, and if the state moves, the signature no longer matches it. That is the difference between a control and a habit.
  - _resolve by:_ researcher decision — needed before base can actually gate lexical
- **`open.base.seed-over-inclusive`** — The seed is deliberately over-inclusive and non-exhaustive — Screen 0 then rejects. But there is no rule for what over-inclusive MEANS, so the seed's breadth is a judgement made per run. (Carried from characteristics.json; the seed lives here now.)
  - _recommendation:_ Bias to over-inclusion and let Screen 0 carry the cost: a false positive is caught by a gate; a false negative is invisible forever. State it as a rule with a measurable seed-recall check (gate.char.seed-recall).
  - _resolve by:_ researcher decision
- **`open.base.stem-master-shape`** — No stem-master table exists in the live DB (plan §4: 'No dedicated stem-master table exists — derive from verse_morphology'). This is a new build, and it is unclear whether the master is a persisted table or a derived view.
  - _recommendation:_ PERSISTED. A derive-on-demand view cannot be signed off, cannot be gated, and cannot carry provenance — and base's whole shape is 'produce it, prove it, sign it off'. Also carried in the plan's parking lot ('Stem-master: first-class persisted table vs derive-on-demand').
  - _resolve by:_ researcher decision; affects Appendix B
- **`open.base.cluster-regenerability`** — base.cluster-assignment is declared not-re-run, but gate.base.regenerable requires base to reproduce exactly when regenerated. A never-re-run assignment cannot be proved that way — and if it were re-run against a changed cluster population it might not reproduce.
  - _recommendation:_ Treat the ASSIGNMENT as regenerable (the rule is stated, so it can be re-derived and compared) but never automatically OVERWRITE an existing one — re-derivation reports a divergence for the researcher rather than silently reassigning. That keeps the gate honest without re-litigating settled membership.
  - _resolve by:_ researcher decision
