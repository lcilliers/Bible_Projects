**Configurator maintenance**

## What it configures

THE SOLE WRITE-PATH TO THE CONFIGURATOR. Authoring, loading, self-validating, versioning, diffing, rolling back — and, per the 2026-07-15 ruling, propagating a config change into the schema it governs. No module writes cfg_* directly; every change to what the application does passes through here and is audited.

**Nodes**

- `process` — How maintenance works: the sole-write-path rule, the load lifecycle, versioning, audit, rollback, schema propagation, and the refusal rules.
- `entities` — What it owns: the rule store, the version register, the change log, the seed manifest.
- `output` — Load reports, version diffs, the migration proposal.
- `validation` — The self-validation battery — the checks that run BEFORE any study run.
- `naming` — Naming parameters.
- `filing` — Filing parameters.

**7 open question(s)**

- **`open.cfgmaint.schema-propagation-safety`** — THE DANGEROUS ONE. The 2026-07-15 ruling makes a config change a schema-change trigger. But a config edit can now imply a DESTRUCTIVE migration: remove a value from enum.role -> the CHECK constraint regenerates -> every existing row holding that value is suddenly invalid. The researcher edits one line of JSON; the utility proposes dropping data.
  - _recommendation:_ B, with A as the floor: nothing narrowing or destructive is ever applied without an impact report and an explicit researcher act. And note the connection — `alias_map` is not documentation, it is THE MIGRATION INPUT: it is what maps rows off a retired value onto its canonical replacement. A narrowing change with no alias_map is incomplete config, and should be REFUSED, not applied.
  - _resolve by:_ researcher decision — blocks any live use of schema propagation
- **`open.cfgmaint.precedence`** — Seed files are the human-editable input; the DB is authoritative at runtime (plan A.1). What happens when BOTH change — a `config set` edit in the DB, then a seed reload that does not know about it? Carried from plan A.8.
  - _recommendation:_ A. It keeps git as the change history (a design goal), makes every change reviewable as a diff, and means there is exactly one direction of flow: seed -> DB. B loses git; C institutionalises drift.
  - _resolve by:_ researcher decision — decides the whole editing model
- **`open.cfgmaint.check-spec-storage`** — `validation.check` is free text ('value-in-domain', 'pair-direction driver->term', 'mandatory-not-absent + self-interpretable'). The validation engine cannot dispatch on free text, and compound checks are jammed into one string with '+'. Carried from ../_manifest.json meta.open.check-vocabulary; this utility is where it lands.
  - _recommendation:_ A. It is inspectable, testable, and each named check is a small unit of code the kernel can confirm exists at load (an unresolvable check = invalid config). B invents a language; C hides logic in SQL where nothing can review it.
  - _resolve by:_ researcher decision — blocks the validation engine
- **`open.cfgmaint.vocab-migration`** — The researcher's 2026-07-15 ruling (a) — 'no custom nomenclature may be added to the configurator without cross-checking its description in the enums' — makes the configurator's OWN vocabularies (governs · kind · status · axis · enforcement · severity) nomenclature like any other. They currently live in ../_manifest.json meta.vocabularies, which is a second home for them, which the same ruling (b3) forbids.
  - _recommendation:_ Migrate the 6 meta-vocabularies first (they have authored descriptions and unblock the kernel). Then author the undeclared ones. The 11 lexical enums are a sourcing job, not a typing job — do them against the live DB, and leave the 3 RECONCILE ones until ruled.
  - _resolve by:_ researcher confirmation of the order; the ruling itself is not in question
- **`open.cfgmaint.one-home-enforceability`** — Layout v2 §2.3 rules that a rule has exactly one home. `gate.cfgmaint.id-unique` catches a duplicated ID — but NOT the same rule restated in prose under two different ids, which is exactly how the four divergent `role` vocabularies happened.
  - _recommendation:_ C + A. C removes the common case structurally; A accepts the residue honestly rather than claiming a gate that does not exist. B is a nice-to-have later, not a foundation.
  - _resolve by:_ researcher decision
- **`open.cfgmaint.bootstrap-order`** — Cold start: the utility must load its own config before it can load anything else, using only the kernel. The order and failure behaviour are unspecified.
  - _recommendation:_ Fixed order: kernel -> this utility's own seed -> _manifest envelope -> wide/enums -> wide/* -> utilities -> processes. Any failure halts the whole load; a partially-loaded config never runs.
  - _resolve by:_ design, once the loader is built
- **`open.cfgmaint.utility-node-shape`** — Utility files here reuse the six process facets. `naming` and `filing` are thin for a utility, and `entities` means something different (its own control tables, not study data).
  - _recommendation:_ Keep the shape — consistency is worth more than a tailored node-set, and the DB flattens all of it to one rule table anyway (../_manifest.json meta.open.rule-table). Revisit only if a utility genuinely cannot express itself.
  - _resolve by:_ researcher evaluation of this file
