**STEP client (access and use of STEP)**

## What it configures

Access to STEP Bible — the application's ONLY external data source. Which APIs exist, which one sources what, how the server is reached, and the constraints its behaviour imposes (the 60-result cap, no cache, no key). Everything the study knows about Scripture in the original languages arrives through here.

**Boundary**

- `util.step` — HOW to reach STEP and what it can do — endpoints, connection, version, limits, caching policy. This file.
- `fetch (process)` — WHAT to fetch and when — Strong's resolution, which terms, retry policy, worklist.
- `raw (process)` — WHAT IS STORED and its controls — immutability, parity, provenance.
- `rule` — One rule, one home (layout v2 §2.3). raw and fetch CITE this utility's rules by id; they never restate them.

**Nodes**

- `process` — How STEP is used: which API for what, the connection, the cap, the caching policy, the version-as-provenance rule.
- `entities` — None of its own — STEP's data lands in the raw process's entities. This utility is a conduit.
- `output` — The fetch log.
- `validation` — The gates: env parity, cap exhaustion, version stamping, API-fit.
- `naming` — Naming parameters.
- `filing` — Filing parameters.

**6 open question(s)**

- **`open.step.parity-baseline`** — gate.raw.source-parity (process/raw.json) cannot run: STEP is a live local server with NO cache, so re-querying it is not a stable baseline. The raw layer is trusted on first ingest, never verified. This is a STEP CAPABILITY question, which is why it lands here.
  - _recommendation:_ A. It is the only option that makes raw genuinely replayable, survives STEP changing or going away, and makes the immutability claim true rather than aspirational. It is also cheap — the payload is small and write-once.
  - _resolve by:_ researcher decision — shared with process/raw.json open.raw.step-parity
- **`open.step.version-is-provenance`** — `version` (default ESV_th) selects which Bible module STEP answers from. It is therefore PROVENANCE of every raw row — but nothing currently records it on the data, and the two-version-variable defect means it was not even reliably known.
  - _recommendation:_ Stamp `step_version` on every raw row at ingest, and make a version change a NEW ingest rather than an update (raw.immutable). Also: is the version a SETTING or an ENUM? Its valid values are defined by STEP, not by IBA — so a setting, but one whose value is provenance, not preference.
  - _resolve by:_ researcher decision; affects the raw schema (Appendix B)
- **`open.step.cap-exhaustion-trust`** — The client self-validates pagination against STEP's reported `total`, and engine/migrate.py carries a STEP_EXHAUST_CHECK flag — but the 60-cap workaround is two layers of canonical section splits, and the docstring records real cases where a half-section STILL exceeded 60 (rāšāʿ H7563: Psalms cut 34/80, Proverbs 60/77).
  - _recommendation:_ Never trust the split depth; trust only the arithmetic. gate.step.cap-exhausted compares rows-returned against STEP's own `total` for EVERY query and red-halts on any shortfall, at any depth. If total is unavailable, that is itself a failure — not a pass.
  - _resolve by:_ researcher decision
- **`open.step.availability`** — STEP is a LOCAL server (localhost:8989). If it is not running, every fetch fails; if it is running a different module set, results change silently.
  - _recommendation:_ A pre-flight: server reachable + the configured version present in its module list + a known-answer probe (a fixed Strong's returning a known gloss). Cheap, and it distinguishes 'down' from 'different'.
  - _resolve by:_ researcher decision
- **`open.step.multi-code-fork`** — How to resolve a Strong's that STEP splits into lettered siblings. OPEN SINCE 2026-07-13; blocks Proverbs I2-closure; every multi-code term is currently under-pulling.
  - _recommendation:_ The filed diagnosis recommends A now (with ruach/H2502 as regression tests) and flags C as the more-correct long-term model. That still reads right — but note WHY C is better: it removes the heuristic entirely by deferring to morphology, which is already the study's declared source of truth (step.is-a-source-not-the-truth). A is a guess that works; C is the principle. If C is affordable, it is the answer.
  - _resolve by:_ researcher decision — carried from 2026-07-13, still open
- **`open.step.related-term-scope`** — The researcher requires 'verses with span for all terms (main and related)'. The current pull fetches verses for MAIN terms only; related terms get {strong, form, gloss, translit} and nothing else — 6 of 9 related codes in the newest pull were never fetched at all.
  - _recommendation:_ B or D. D is cleanest — it says a related term is either worth onboarding (and then it IS a term, with the same rules) or it is a pointer, and pointers do not carry evidence. That removes the category rather than special-casing it. A is a scope explosion for terms the registry never chose; the 666-related-words figure for one word is the warning.
  - _resolve by:_ researcher decision — this is a SCOPE call, and it changes how much of Scripture the study pulls
